# راهنمای دانشجوی پروژه‌ی DeepCore

## ۱. هدف و خروجی مورد انتظار

ربات از خانه‌ی `S` شروع می‌کند، همه‌ی معدنچی‌های `M` را نجات می‌دهد و در `E` قرار می‌گیرد. یک جواب فقط وقتی معتبر است که هر دو شرط برقرار باشند: `state.miners` خالی باشد و ربات روی `E` باشد.

شما دو فایل را کامل می‌کنید:

| فایل | مسئولیت |
| --- | --- |
| `src/deepcore/solver.py` | DFS، IDS، Bidirectional، UCS، GBFS، A* و دو بخش امتیازی |
| `src/deepcore/heuristics.py` | `h1_basic` و `h2_advanced` |

`breadth_first_search` و `h_naive_manhattan` نمونه‌های مرجع هستند. آن‌ها را بخوانید تا قرارداد محیط و `SearchMetrics` را ببینید.

## ۲. راه‌اندازی و اجرای پروژه

پس از استخراج فایل پروژه، در پوشه‌ی ریشه فقط اجرا کنید:

```powershell
python main.py
```

در منوی بازشده، گزینه‌ی ۱ نمونه‌ی BFS، گزینه‌ی ۲ آزمون‌ها و گزینه‌ی ۴ مسیر راهنما را نشان می‌دهد. برای اجرای مستقیم نیز می‌توانید بنویسید:

```powershell
python main.py --algo astar --map level1 --heuristic h1
python main.py --benchmark --map all
```

برای دیدن رابط گرافیکی، `python main.py --gui` را اجرا کنید؛ وابستگی‌های موجود در `requirements.txt` پیش از اجرای پروژه به‌صورت خودکار نصب می‌شوند. پروژه از `pygame-ce` استفاده می‌کند که با Python 3.14 نیز سازگار است و در کد با `import pygame` استفاده می‌شود. نام نقشه‌ها `level1` تا `level5` است. برای خواندن نقشه‌ی خودتان، مسیر فایل متنی نقشه را به `--map` بدهید.

## ۳. قوانین محیط و هزینه‌ها

| نماد | معنا | اثر |
| --- | --- | --- |
| `#` | دیوار | عبورناپذیر |
| `.` | تونل عادی | هزینه‌ی پایه ۱ |
| `~` | لجن سمی | هزینه‌ی پایه ۵ |
| `B` | تخته‌سنگ | با `PUSH_*` جابه‌جا می‌شود؛ هزینه‌ی پایه ۶ |
| `O` | پرتگاه | عبورناپذیر؛ هل دادن سنگ داخل آن، پل می‌سازد |
| `@` | آوار | با `DRILL_*` پاک می‌شود؛ هزینه ۱۰ |
| `M` | معدنچی | ورود به خانه او را سوار کپسول می‌کند |
| `E` | آسانسور | محل پایان |

اگر `k = state.carried` باشد، هر حرکت یا هل دادن، علاوه بر هزینه‌ی پایه، `2k` هزینه دارد. هزینه‌ی حفاری مستقل از بار و برابر ۱۰ است. جزییات رسمی و تصویر محیط در [assignment.html](assignment.html) آمده است.

## ۴. قرارداد API

`DeepCoreState` تغییرناپذیر و قابل هش است؛ از خود شیء حالت در `set` و `dict` استفاده کنید. هیچ فیلدی را mutate نکنید.

```python
start = env.get_initial_state()
for action, child, step_cost in env.get_successors(state):
    # action.value یک رشته مانند "MOVE_N" است
    pass

if env.is_goal(state):
    ...
```

هر تابع جست‌وجو باید یک `SearchMetrics` برگرداند. در جواب موفق، حداقل این فیلدها را پر کنید:

```python
SearchMetrics(
    solved=True,
    solution_actions=["MOVE_N", ...],
    total_cost=...,
    nodes_expanded=...,
    nodes_generated=...,
    max_frontier_size=...,
    max_memory_size=...,
)
```

برای Bidirectional Search از همه‌ی حالت‌های برگشتی `env.get_goal_states()` به‌عنوان ریشه‌های جستجوی پسرو استفاده کنید؛ حالت هدف یکتا نیست، چون ممکن است آوار، سنگ‌ها یا پل‌های غیرضروری در جواب‌های معتبر متفاوت باشند. سپس از `env.get_predecessors(state)` استفاده کنید. هر سه‌تایی برگشتی `(action, previous_state, step_cost)` تضمین می‌کند که اجرای `action` از `previous_state` به `state` می‌رسد. هنگام اتصال دو نیمه، actionهای نیمه‌ی عقب را به ترتیب حرکت از نقطه‌ی تلاقی تا یکی از حالت‌های هدف برگردانید و هزینه‌ی همان انتقال‌ها را حفظ کنید.

## ۵. ترتیب پیشنهادی پیاده‌سازی

1. DFS را با stack و مجموعه‌ی explored بنویسید.
2. IDS را با depth-limited DFS و مجموعه‌ی حالت‌های مسیر بنویسید. هر عمق باید از ابتدا دوباره اجرا شود.
3. UCS را با `heapq` و جدول بهترین `g` بنویسید. آزمون هدف هنگام pop شدن از صف است.
4. GBFS را فقط با `h(n)` اولویت دهید.
5. A* را با `g(n) + h(n)` بنویسید؛ اگر مسیر ارزان‌تر به یک حالت پیدا شد آن را بازگشایی کنید.
6. Bidirectional Search را با frontier پیشرو و پسرو و نقشه‌ی والد جدا پیاده‌سازی کنید.
7. بخش امتیازی: Weighted A* و IDA*.

در تمام الگوریتم‌ها، مسیر را با map والد بازسازی کنید. برای priority queue یک شمارنده‌ی افزایشی به tuple اضافه کنید تا مقایسه‌ی مستقیم `DeepCoreState` به ترتیب ناخواسته وابسته نباشد.

## ۶. طراحی هیوریستیک

`h_naive_manhattan` خط مبنا است. `h1_basic` باید یک کران پایین قابل قبول بسازد؛ یک راه مناسب، MST روی ربات، معدنچی‌های باقی‌مانده و آسانسور، به‌اضافه‌ی کمینه‌ی جریمه‌ی بار است. `h2_advanced` باید بر `h1` غلبه کند و همچنان بیش‌برآورد نکند. فاصله‌ی دیوارآگاه، هزینه‌ی اجتناب‌ناپذیر مانع و تشخیص بن‌بست ایده‌های مناسب هستند. در هزینه‌ی مانع فقط هزینه‌ی افزایشی `PUSH` یا `DRILL` را اضافه کنید؛ هزینه‌ی حرکت ربات یا حرکت روی پل را که در MST/فاصله حساب شده دوباره نشمارید. اگر چند مانع یا مسیر ممکن است، کمینه‌ی هزینه‌ی لازم را انتخاب کنید.

SMA* در صورت اعلام مدرس یک الگوریتم امتیازی/اختیاری است و جایگزین الگوریتم‌های اصلی نیست. در این بخش باید محدودیت حافظه، حذف کم‌امیدترین برگ و بازیابی مقدار `backed-up` را توضیح دهید.

برای هر حالت هدف باید `0` برگردانید. انتظار آزمون عمومی این است:

```text
0 <= H0(s) <= H1(s) <= H2(s) <= optimal_cost(s)
```

## ۷. آزمون و گزارش

آزمون‌های عمومی در `tests/test_search.py` هستند. آن‌ها صحت پاسخ، هزینه‌ی UCS، طول مسیر IDS و Bidirectional، قابلیت قبول هیوریستیک و بهینگی A* را بررسی می‌کنند. تغییر این فایل‌ها اعتبار آزمون شما را نشان نمی‌دهد.

گزارش باید شامل مدل‌سازی مسئله، انتخاب ساختمان داده، تحلیل کامل بودن و بهینگی، پیچیدگی زمانی و فضایی، اثبات یا استدلال قابل قبول بودن هیوریستیک‌ها، و جدول نتایج در هر پنج نقشه‌ی `level1` تا `level5` باشد. در جدول حداقل الگوریتم، `solved`، تعداد گام، هزینه، `nodes_expanded`، تعداد گره‌های تولیدشده و `max_frontier_size` یا بیشینه‌ی حافظه‌ی جستجو را بنویسید. معیار نمره‌دهی به زمان اجرای سیستم وابسته نیست: زمان در صورت گزارش فقط اطلاعات جانبی است و امتیاز ندارد. ابتدا درست بودن جواب، برابری هزینه‌ی A* و UCS، قابل قبول بودن و غلبه‌ی هیوریستیک‌ها بررسی می‌شود؛ بعد بهبود قطعی تعداد بسط‌ها و مصرف حافظه نسبت به خط مبنا با میانگین حسابی پنج نقشه مقایسه می‌شود. درصد ثابت کاهش، شرط قبولی مستقل نیست.
